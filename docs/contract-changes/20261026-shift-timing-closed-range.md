# Contract change: the range of `content.shiftTiming` is closed, and `import.start` focus is described

- Date: 2026-10-26
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.7` (wire version `1.0`), a correction of the text inside the release candidate; the
  tag `spec-v1.0.0-rc.7` is set by the maintainers after approval and is not set yet.
- Implementation lines changed with it: `plugins/opentune/skills/beat-grid/scripts/beat-grid.mjs` (the ranges of the
  timing plan) and the text of two skills. `src/` and `mock/` are not part of this change.

## Background

Two statements of the specification were missing or incomplete, found when the skill texts of the previous change were
reviewed.

**The range of `content.shiftTiming`.** The method moves every time-grid handle whose output position lies in `range`.
The OpenTune build selects the handles with `start <= position <= end`, so the range is a closed interval: a handle
exactly at either end moves. The schema description only said "lies in range". A client that sends two ranges that
share an end point (the natural way to cut a vocal into neighbouring phrases) moves the handle at that point twice,
once by each call. The `beat-grid` skill did exactly that: it planned the range of every chain up to the start of the
next one, so neighbouring ranges met at one point.

**The `focus` member of `import.start`.** The description said that `focus` selects the last imported clip, as the UI
does. PROTOCOL.md section 21 rule 2 says more: the clip is loaded into the piano roll, and the view is not switched. The
schema did not say the second half, which a client reading only the method schema could not know.

This change writes down the existing behaviour. No behaviour of OpenTune, no param, no result member, no method,
capability, error kind, warning code or reason code changes, and no vector changes.

## Interoperability

- A server and a client of the earlier text keep working: the text now states what a real OpenTune build did before. A
  client that already sent adjacent ranges that share an end point, to a real build, got the double move already; it can
  now see why in the specification.
- The timing plan of the `beat-grid` skill changes its output slightly: a range that used to end exactly where the next
  one starts now ends 0.1 ms earlier, and a chain that has no room for a range appears in `warnings` instead of in
  `suggestions`. `opentune_edit_timing` and the OTCP methods are not touched.
- The mock of this repository selects the handles of a shift with `start <= position < end` (half open), which differs
  from the build at the end point. No vector depends on the difference, and the mock is not part of this change; it is
  noted here so that the next change to `mock/timing.ts` makes it closed.
- The fork's copy of the specification, pinned by hash, is synced by the maintainers.
