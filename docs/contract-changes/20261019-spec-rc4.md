# Contract change: OTCP specification 1.0.0-rc.4

- Date: 2026-10-19
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.3` → `1.0.0-rc.4` (wire version `1.0`, unchanged). The tag `spec-v1.0.0-rc.4` is set by the maintainers after approval.
- Implementation lines changed with it: `mock/arrangement.ts`, `mock/edit.ts`, `mock/import.ts`, `mock/model.ts`, `mock/reference.ts`, `mock/server.ts`, `mock/tracks.ts`, `mock/ui.ts`.

## Background

Implementing the arrangement, track, transport and interface methods in OpenTune, and checking them against a real build, showed one failure without a reason code (reference analysis) and several places where the text or the vectors differed from what OpenTune does. This release candidate records them; it adds no method, member or capability.

## Interoperability

Both versions are release candidates of the same wire version `1.0`; clients decide by capabilities, not by version (PROTOCOL.md section 2.3 rule 5).

- A client of rc.3 with a server of rc.4 sees three new reason codes under the error kinds it handles already (`NOT_READY`, `ANALYSIS_FAILED`); `retryable` tells it whether to retry. `activeTrackId` is a number in the UI snapshot where rc.3 vectors expected null before the first selection, which the schemas always allowed.
- A client of rc.4 with a server of rc.3 may see `NOT_READY` or `INTERNAL` without these reasons for the same cases (PROTOCOL.md section 12.6 rule 6) and relies on the error kind and `retryable`.
- Where the boundary of a merge does not lie on a frame of the analysis, a server of rc.3 still gives a recipe for the merge. A client that applies it gets the clips back, but the position of the cut snaps to the nearest frame of the analysis; a server of rc.4 reports `revert` null with `IRREVERSIBLE` there.
