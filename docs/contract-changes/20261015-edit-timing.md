# Contract change: opentune_edit_timing

## Background

This change adds `opentune_edit_timing`, the write tool for the time grid of a clip: the time handles that stretch or
compress the audio between them, as OpenTune's time tool does. It extends the frozen `tools/list` catalog and adds
write-result rendering snapshots. The OTCP specification (`spec/otcp/v1/`) and the MCP instructions are not changed.

OpenTune does not detect beats. Handle positions come from the user, or from `seed`, which places the initial handles
where OpenTune's time tool does; the tool never computes positions of its own.

## Tool surface

`opentune_edit_timing` takes `clip` (placement id `p:...` or content id `c:...`), `expected_revision` (the
`clip_revision` of the clip; required for `shift` and `move`), `ops[]` (1 to 8), `wait_seconds` (seed only, 0 to 30,
default 10) and `instance_id?`. It needs the `timing.v1` and `jobs.v1` capabilities and calls `content.shiftTiming`,
`content.editTimeGrid`, `job.get` and, to resolve a placement id, `project.get`.

| Op      | Fields                                                                                                          | OTCP                                     |
| ------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `seed`  | none                                                                                                            | `content.editTimeGrid` op `seed` (a job) |
| `shift` | `start_output_sec` + `end_output_sec`, or `start_content_sec` + `end_content_sec`; `delta_ms` (-10000 to 10000) | `content.shiftTiming`                    |
| `move`  | `moves[]` of `handle_id` and `output_sec` (1 to 64)                                                             | `content.editTimeGrid` op `moveHandles`  |

## Behaviour

- **Revisions.** Only the grid part of the `clip_revision` is forwarded (`expectedGridRevision`). A change of the
  notes, the key or the clip position therefore does not conflict with a timing edit; a change of the grid does
  (`REVISION_CONFLICT`, reason `grid_changed`).
- **Seed.** `seed` must be the only op, because it changes the grid revision. It starts the `timeGridSeed` job and
  waits up to `wait_seconds`: a finished job returns the write result of the seeding, a failed job returns its error
  with the job in the context, a cancelled job returns a success that says no handles were written, and a job still
  running returns the write envelope that names the job (follow it with `opentune_get_job`). Seeding cannot be undone;
  the first sentence of the result says so.
- **Several ops.** `shift` and `move` ops run in order, each as its own OTCP call and its own undo step, each with the
  grid revision the previous one returned. The whole request is checked before anything is sent. If a later op is
  refused, the error says how many ops had been applied (`executed: true`) and `completed` lists their results.
- **Limits.** A move limited by the minimum spacing is applied as far as allowed; the result shows the requested and
  the applied position (`clamped`, the change table and the warning `CLAMPED`).
- **Result.** One op: the rendered write result plus `clip_revision` (valid for the next edit). Several ops: `summary`,
  `steps[]` (one rendered write result each) and `clip_revision`.
- **Next steps.** `grid_not_seeded` points to `seed`; `grid_changed` points to reading the clip again.

## Compatibility

A new tool: existing clients and tools are unaffected. A build without `timing.v1` answers
`UNSUPPORTED(capability_missing)` with the usual next step.
