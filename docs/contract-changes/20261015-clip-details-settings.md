# Contract change: opentune_get_clip_details and opentune_get_settings

## Background

This change adds two read-only tools to the frozen `tools/list` catalog: `opentune_get_clip_details`, which reads the
state of one clip besides its notes, and `opentune_get_settings`, which reads the global settings of the OpenTune
installation. The OTCP specification (`spec/otcp/v1/`) and the MCP instructions are not changed. Existing catalog
entries are unchanged.

## Files

| File                          | Change                                                           |
| ----------------------------- | ---------------------------------------------------------------- |
| `test/golden/tools-list.json` | Appends `opentune_get_clip_details` and `opentune_get_settings`. |
| `docs/reference.md`           | Regenerated by `npm run catalog:update`.                         |
| `mcpb/manifest.json`          | Tools list synced from the golden catalog.                       |

## Tool surface

`opentune_get_clip_details` takes `clip` (placement id `p:...` or content id `c:...`), `sections[]` (any of `key`,
`pitch_shift`, `analysis`, `render`, `time_grid`, `reference`, `auto_modes`; default all) and `instance_id?`. It needs
`read.v1` and calls `content.getDetails` and, for a placement id, `project.get` (for the geometry part of the
revision). `content.getDetails` has no sections parameter: the sections select members of its result. The result
always has the ids, `durationSec` and `clip_revision` (the same value `opentune_get_notes` returns, usable as
`expected_revision`). Values that cannot be determined are `null` with a reason in `nullReasons`. The time grid lists at
most 200 handles; `handleCount` gives the number and `handlesTruncated` marks a cut list.

`opentune_get_settings` takes `sections[]` (`processing`, `audio_device`, `recent`, `export_caps`, `log`; default all but
`log`), `log_lines?` (1 to 500, default 100) and `instance_id?`. It calls `session.info` always, `prefs.get` for
`processing` and `recent`, `audio.get` for `audio_device` and `app.getLog` for `log`.

| Section        | Source                                        | Without the capability                    |
| -------------- | --------------------------------------------- | ----------------------------------------- |
| `processing`   | `prefs.get` merged with `session.info`        | `session.info` values only (`read.v1`)    |
| `audio_device` | `audio.get`                                   | `null`, `capability_missing:audio.device` |
| `recent`       | `prefs.get`                                   | `null`, `capability_missing:read.v1`      |
| `export_caps`  | `session.info` (`import`, `export`, `limits`) | always available                          |
| `log`          | `app.getLog`                                  | `null`, `capability_missing:read.v1`      |

A section whose capability is missing does not fail the call. When the log would make the result larger than 20,000
characters, the oldest lines are left out and the summary says how many.

## Behaviour

- **Untrusted strings.** Recent project paths, device names and log lines are returned only as JSON string values; the
  summary sentences contain only counts and names of enumerated values.
- **Residual reference binding.** The specification says the AUTO button runs the reference mode only when the instance
  reports `reference.v1`. It does not say what the button runs for a clip that still has a reference binding on an
  instance without that capability. The result then carries the warning `RESIDUAL_REFERENCE_BINDING` that says so; it
  adds no field of its own.

## Compatibility

Additive: older clients see two more tools. Both tools need only capabilities that the instances already report
(`read.v1`, `session.v1`; `audio.device` for the audio device section). No OTCP method is added or changed.
