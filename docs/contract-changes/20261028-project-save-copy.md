# Contract change: project.saveCopy (OTCP 1.0.0-rc.8)

- Date: 2026-10-28
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.7` → `1.0.0-rc.8` (wire version `1.0`, unchanged). `1.0.0-rc.8` is unreleased; its section in
  the changelog is dated when the maintainers fix the text. The tag `spec-v1.0.0-rc.8` is set by the maintainers after approval.
- Implementation lines changed with it: this commit changes the specification only. The mock, the tools and the tests that use
  the method follow in the same pull request (`20261028-autosave-and-save-rules.md`).

## Background

An agent that saves after every finished step overwrites the project file the end user works with. A short test showed the
consequence: the end user asked for a change to be dropped, and the agent had already saved it over the file, so the answer
"do not save" no longer meant anything. The decision of the end user was to write an additional copy after every step, at most
50 of them, "like the autosave of Cubase", so that no progress is lost and the original file is never damaged, and to ask
now and then whether the main file should be overwritten. The old main file goes into a folder `oldversion` of the project,
with at most 10 old versions.

`project.saveAs` cannot write such a copy. It does what Save As in OpenTune's file menu does: after the write it makes the new
path the project's file (the window title and the next Save follow it), clears the unsaved-changes flag (the end user is no
longer reminded when closing, although the main file was not saved) and puts the path on the recent-projects list (which 50
copies would fill). The write itself does none of this: the code of OpenTune that takes the snapshot of a project and
writes it to a given file leaves the current project file, the flag and the list alone, and the handler of the editor's
save command does the three things after it. A method that only writes the file is therefore new interface code and does
not change OpenTune's own logic.

This change adds one method, one capability and one job kind. Nothing is removed or renamed, and no error kind, reason or
warning code is added.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. The method is new and the capability tells a client whether
an instance has it (PROTOCOL.md section 2.3 rule 5 and section 7 rule 1), so nothing depends on the version number.

- A client of rc.7 with a server of rc.8 never sends `project.saveCopy` and sees what it saw before, plus one more capability in
  `session.hello`, which it ignores.
- A client of rc.8 with a server of rc.7 does not find `project.copy` in `session.hello` and does not send the method. A client
  that sends it anyway gets `UNSUPPORTED(unknown_method)` from such a server, and nothing is written. The client does not fall
  back to `project.saveAs`, which would make the copy the project's file.
- The unofficial OpenTune test build must implement `project.saveCopy` and report `project.copy` once it can write a copy
  without making the copy the project's file, clearing the unsaved-changes flag or adding the copy to the recent list; its
  copy of the specification and its runner are updated separately. Until then it follows rc.7 and answers as above.
- The job kind `projectCopy` is new in the job object. A client that lists jobs and does not know the kind treats it as it
  treats any kind it does not know (section 2.3).
