# Contract change: autosave copies and save rules in the tools, the instructions and the skill

- Date: 2026-10-28
- Frozen surfaces: the `tools/list` snapshot (`test/golden/tools-list.json`), the instructions snapshot
  (`test/golden/instructions.txt`) and the result snapshots of the save tools (`test/golden/project-files/*.json`).
- Related: `20261028-project-save-copy.md` (the OTCP method `project.saveCopy`, specification `1.0.0-rc.8`).
- Tool names, the set of tools and the required arguments do not change.

## Background

A short test with a real OpenTune showed two problems. First, the instructions told the agent to save after every
finished step, so the agent overwrote the project file the end user works with. The end user then asked for the last
change to be dropped, and answering "do not save" no longer meant anything, because the change was already in the file.
Second, the agent did not find the way to duplicate a track: the description of `opentune_set_tracks` mentioned
duplicating only in its fourth sentence, and the description of `opentune_edit_arrangement` offered `copy`, which copies
clips and not a track. A third finding was that the next step of a refused merge did not say that the two clips must have
the same key, so the agent could not get past `merge_not_possible`.

The decision of the end user was to write an additional copy of the project after every step, at most 50 of them, so that
no progress is lost and the original file is never damaged, and to ask now and then whether the main file should be
overwritten. The main file that is overwritten goes into a folder `oldversion`, with at most 10 old versions.

### Result members of the save tools

- `opentune_save_project` with `mode: autosave` returns the write envelope of the start of the copy (`applied` false: the
  project did not change), `job`, and: `autosave` (`path`, `number`, `folder`, `keep`, `sizeBytes`, `removedOlder`,
  `couldNotRemove`), `projectPath` and `projectDirty` as they are after the copy, `notSavedInProject`, `mediaFolder` (the
  `Project_Media` folder inside the autosave folder), and `nullReasons` when a member is `null`. The first sentence says
  which copy was written, that the project file was not changed and whether the project still has unsaved changes.
- The other save tools get the member `oldVersion`: `{path, folder, keep, removedOlder, couldNotRemove}` when a file was
  replaced, or `null` with `nullReasons.oldVersion` `no_previous_file` when no file existed at the target. The first
  sentence no longer says that the previous content cannot be restored when an old version was kept; it says where the
  copy is, with the path as data in `oldVersion.path`.
- Errors: `IO_ERROR` with the reason `backup_failed` (the old version could not be kept; nothing was saved; the file is
  unchanged) and with `write_failed` (the autosave folder could not be made); `INVALID_ARGUMENT` with `no_project_path`
  (autosave of a project that was never saved) and `project_path_unusable`; `UNSUPPORTED` with `capability_missing` and
  its own next step for `project.copy`. A client accepts reasons it does not know.

## Interoperability

- A client that reads the earlier results keeps working: the members it knows are unchanged, and `oldVersion`,
  `autosave`, `projectPath` and `projectDirty` are new members that it may ignore. The wording of the first sentence of a
  save result changes.
- With an OpenTune test build of `1.0.0-rc.7` or older (no capability `project.copy`) the mode `autosave` fails with
  `UNSUPPORTED` (`capability_missing`) before anything is written, and the next step tells the agent not to call it
  again and to remind the user to save. The other modes work as before and also keep old versions: that needs only the
  file system, not the new method.
- Keeping an old version needs the server process to read the project file and write into the project's folder. When it
  cannot, a save that would replace the file is refused with `backup_failed`. Before this change such a save went through
  without a copy. Saving under a new path where no file exists is not affected.
- The server writes into the project's folder only inside `<name>.autosave` and `<name>.oldversion`, and deletes only
  files that match `<name>-autosave-<number>.otproj` and `<name>-<YYYYMMDD-HHMMSS>[-<n>].otproj` in them. The copy of the
  audio that OpenTune makes into `Project_Media` next to a written file now also happens inside `<name>.autosave`; the
  server never deletes it.
