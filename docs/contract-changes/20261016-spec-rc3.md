# Contract change: OTCP specification 1.0.0-rc.3

- Date: 2026-10-16
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.2` → `1.0.0-rc.3` (wire version `1.0`, unchanged). The tag `spec-v1.0.0-rc.3` is set by the maintainers after approval.
- Implementation lines changed with it: `mock/reads.ts`, `mock/reference.ts`, `mock/placements.ts`, `mock/arrangement.ts`, `mock/tracks.ts`, `mock/export.ts`, `mock/server.ts` (test interface `removeClip`), `src/render/text.ts` (one table entry for the new warning code), `test/support/fake-opentune.mjs`, `test/unit/mock-reference.test.ts`, `test/unit/mock-export.test.ts`.

## Background

Implementing the methods of layers L2 to L5 in OpenTune, and testing them against a real OpenTune build, showed where rc.2 did not match what OpenTune does, which failures had no reason code, and where the text left a choice open. This release candidate writes these points down. The rule for each point was: what the implementation in OpenTune already does reliably becomes the specification, and the vectors follow it; where the implementation would have to change its behaviour, the normative text stays as it is (or gains a reason code that implementations may leave out for now), the current behaviour is stated, and the change is left to a later implementation step.

Points settled here:

1. Hybrid mode is a boolean in `prefs.get`, `session.info` and the export result. Its effect, a pitch shift instead of the vocoder for small corrections, is described as information; the threshold OpenTune uses is not part of the protocol.
2. `content.getDetails` `timeGrid.minHandleSpacingSec` was optional, although every implementation can report it. It is now required, and null with a reason when it cannot be determined.
3. A change without an undo entry clears the redo history (section 15.3 rule 9), while the OpenTune UI keeps its redo history when the key is changed there. The rule stays; the difference is stated.
4. The mode that OpenTune's AUTO button runs: an instance without `reference.v1` reports `regenerate` where the button runs reference alignment because of a binding left on the clip. The text tells clients how to detect it.
5. Deleting clips or a track removes contents that no other clip shows; section 14.4 rule 6 already required them in `removed`, but three vectors listed only the clips.
6. A hidden track that holds clips (vector `track/duplicate-target-occupied`) is reachable in OpenTune: opening a project keeps the number of shown tracks.
7. The referenceAnalysis job of `content.autoTune` and `content.analyzeReference` repeats the checks of the call, so its errors are those of the checks, not `INTERNAL`. The order of these checks is not part of the contract.
8. Two methods start referenceAnalysis jobs with different results; the result is defined by the starting method.
9. `import.start` differs from the UI's import in two intended ways (notes in the openDyne scheme, positions in layout separateTracks), and it repeats a commit that OpenTune refuses because of a clip id that the project already uses.
10. A pitch shift moves the pitches that `content.getNotes` and `content.getPitchCurve` return without changing `revision`; their cursors are bound to it.
11. `setTargetPitch` and `snapToScale` of `content.editNotes` set the base pitch, while OpenTune's snap (and `content.autoTune` mode `snapNotes`) keeps it and sets the offset.
12. Exports of contents with a stretched time grid, and two early failures that had no reason.
13. Seeding the time grid: the failures of OpenTune's timing analysis, the no-op seed, and the experimental features.
14. `clipKey` on a content without a key, and `undoId`s of UI entries once OpenTune's history is full.
15. Exports without audio, the `noAccess` precondition on Windows, and loaded media on a volume that is not available.
16. The commit retry of `import.start` had no warning code.
17. Values in `changes[].fields.*.after` equal what a read returns afterwards; how OpenTune adjusts notes when it commits them.
18. `detectedMidi` keeps its fraction; how values are rounded.
19. Capability filtering of vectors also for `extraCapabilities`.

## Interoperability

Both versions are release candidates of the same wire version `1.0`; clients decide by capabilities, not by version (PROTOCOL.md section 2.3 rule 5).

**Client of rc.2 with a server of rc.3.**

- The new reason and warning codes, `timeGrid.nullReasons` and the content entries in `removed` are additions that clients ignore or accept (section 2.3 rules 1 and 2). A client of rc.2 that counted the entries of `removed` after a deletion as clips must look at `entity`.
- A client of rc.2 that exported a track without clips received a file without audio; it now gets `INVALID_ARGUMENT(nothing_to_export)`, an error kind it handles already.
- Failed referenceAnalysis and timeGridSeed jobs report the kind of the failed check instead of `INTERNAL`; clients that treated `INTERNAL` as the only failure keep working, because unknown or other kinds are handled like errors anyway.
- A client that assumed a cursor of `content.getNotes` stays valid across a pitch shift now gets `REVISION_CONFLICT(cursor_stale)` and reads again, as after any other change.

**Client of rc.3 with a server of rc.2.**

- A server of rc.2 may omit `timeGrid.minHandleSpacingSec`; a client treats a missing value like null.
- A server of rc.2 may list only the clips in `removed`, export a track without clips as a file without audio, report job failures as `INTERNAL`, and send the failures that now have reasons without a reason. Clients rely on the error kind and on `retryable`.
- A server of rc.2 may let a cursor continue across a pitch shift; a client that changes the pitch shift reads the notes again from the first page.

**OpenTune's implementation (fork).** It already reports `timeGrid.minHandleSpacingSec`, rounds `Midi` and `Cents` values to 4 decimal places, reads `after` back from the committed state, binds the cursors to the pitch shift, sends every seed through a job and refuses exports without audio and exports while a loaded media file's identity cannot be read. It does not send the new reasons and the new warning yet, which rule 11 of section 19 and the method descriptions allow for this release candidate; it does not implement the methods of layer L6 yet, whose vectors (the content entries in `removed`) it follows once it does. The byte-identical copy in the fork (`Tests/Control/spec/otcp/v1/`) and its lock are updated by the maintainers after the tag; this change does not touch them.
