# Contract change: OTCP specification 1.0.0-rc.6

- Date: 2026-10-25
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.5` → `1.0.0-rc.6` (wire version `1.0`, unchanged), proposed as the text of 1.0.0.
  The tag `spec-v1.0.0-rc.6` is set by the maintainers after approval.
- Implementation lines changed with it: `mock/prefs.ts`, `mock/model.ts`, `mock/reads.ts`, `mock/server.ts`,
  `mock/given.ts`, `mock/audio.ts`, `mock/edit.ts`, `mock/export.ts`, and one line table in
  `src/errors/reason-retryable.ts`.

## Background

OpenTune's preferences window has four processing preferences that `prefs.set` could not reach: the vocoder weight, the
rendering priority, the pitch model and the reference alignment mode. An agent that wants to use a different vocoder
weight, or to put rendering on the CPU, had no protocol method for it. This release candidate adds them, together with
the list of values the installation accepts (`prefs.get`), the second kind of failure of a preferences job (the vocoder
does not become ready again) and the vectors that were still missing for settings that the specification has had since
rc.1: the note split of `content.autoTune`, two note parameters, the experimental features and the audio device
members. It adds no method, capability, error kind or warning code; it adds optional members, one result member and
two reasons.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. The new members are optional, and clients decide by
capabilities, not by version (PROTOCOL.md section 2.3 rule 5). The members belong to the release candidates of
1.0.0, so no new capability comes with them; the capability of `prefs.set` stays `prefs.write`.

- A client of rc.5 with a server of rc.6 sends none of the new members and sees what it saw before, with three
  additions that its rules already cover: the result of `prefs.get` has the member `processing.options` (unknown result
  members are ignored, section 2.3 rule 1), the reasons `option_unavailable` and `vocoder_not_ready` can appear
  (unknown reasons are accepted by the kind, rule 2), and a `prefsApply` job can now fail with
  `MODEL_UNAVAILABLE(vocoder_not_ready)`, a kind that `prefs.set` did not list before and that clients treat by its
  `retryable` value. The `warnings` of a result may hold `EXPERIMENTAL_FEATURE`, registered since rc.1.
- A client of rc.6 with a server of rc.5 gets `INVALID_ARGUMENT(invalid_params)` from `prefs.set` when it names
  `vocoderWeight`, `renderingPriority`, `f0Model` or `referenceAlignMode`, because the server rejects unknown params
  members (section 2.3 rule 3), and nothing is changed. `prefs.get` of such a server has no `processing.options`, which
  is why the member is not in `required`: a client reads the member only where it is present and otherwise cannot
  know the accepted values.
- OpenTune's implementation (the test build) is changed separately. Until it implements the members, a build of the
  previous version answers a call with a new member as an rc.5 server does. Its copy of the specification and the
  runner that applies the new preconditions are updated separately.
- The mock changes only what the contract names and one deviation from the specification: a `vibratoRateHz` change now
  reports the unit `hz` (the schema of `content.editNotes` and OpenTune use it).
