# Contract change: OTCP specification 1.0.0-rc.2

- Date: 2026-10-14
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.1` → `1.0.0-rc.2` (wire version `1.0`, unchanged). The tag `spec-v1.0.0-rc.2` is set by the maintainers after approval.
- Implementation lines changed with it: `src/otcp/framing.ts` (shared line decoder), `mock/jobs.ts` (one member of a synthesized job result), `mock/given.ts` (one new history precondition), `test/unit/framing.test.ts`.

## Background

`1.0.0-rc.1` defined the methods of layers L2 to L5 and listed `ui.getState`, `ui.dismiss` and the methods of layers L6 and L8 as planned, without a normative shape. This release candidate defines all of them, so that every method of protocol major 1 has a schema, and it completes the reference mode of `content.autoTune`, which depends on `content.analyzeReference`.

The review of `1.0.0-rc.1` left questions open that this release candidate answers:

1. An undo entry recorded through the API, marked `possiblyStale`, whose track did not move: rc.1 did not say whether `edit.undo` without `force` applies it, warns or refuses it, and a client could not tell in advance. The answer is defined together with the barrier that `track.delete` sets.
2. Export results did not say which revision of each content the file holds, although edits made after `export.start` and before all contents are ready do reach the file.
3. Whether a vector runner filters by capability before or after `given` removes capabilities (`withoutCapabilities`).
4. How a line is judged whose JSON strings escape a lone surrogate (for example `"\ud800"`). Common JSON parsers accept such strings although they encode no Unicode text.

## Interoperability

Both versions are release candidates of the same wire version `1.0`; clients decide by capabilities, not by version (PROTOCOL.md section 2.3 rule 5).

**Client of rc.1 with a server of rc.2.**

- The new methods are behind capabilities that rc.1 already registered (`ui.bridge`, `transport.v1`, `arrangement.v1`, `tracks.v1`, `reference.v1`, `project.io`, `prefs.write`, `audio.device`). A client of rc.1 that never calls them is unaffected.
- `contents` in the export job result, `singleton` in entity references and the new reason and warning codes are additions; clients ignore members they do not know and accept unknown codes (section 2.3 rules 1 and 2).
- Stale undo entries: a client that handled `UNDO_CONFLICT(stale_entry)` keeps working. It sees that error only for entries that are reported as `possiblyStale`; entries recorded through the API whose tracks did not move are no longer possibly stale and are applied as before.
- Lone surrogates: senders were already not to emit text that is not Unicode; a client that sends such escapes now gets `INVALID_ARGUMENT(parse_error)`.

**Client of rc.2 with a server of rc.1.**

- A server of rc.1 that provided some of the planned methods provisionally may answer with other shapes; section 22 requires it to follow these schemas from rc.2 on. Clients validate results against the open forms and treat a capability as the promise of the rc.2 shape only once servers have moved to rc.2.
- A server of rc.1 sends export job results without `contents`. A client that needs the revisions of an export treats a missing `contents` as unknown until its servers implement rc.2.
- A server of rc.1 may accept lone surrogate escapes; clients of rc.2 do not send them.

**Mock, contract runner and fork.**

- The test mock reports `session.v1`, `jobs.v1`, `read.v1` and `history.v1`. The new vectors of these capabilities, among them `session/parse-error-lone-surrogate` and the stale-entry vectors, pass against it; the vectors of the other capabilities are skipped. Mock behaviour for the new methods follows with the mock's own changes.
- Runners decide whether a vector applies from the capabilities reported before `given` is established (vectors/README.md), as the contract runner of this repository already does.
- The byte-identical copy in the fork (`Tests/Control/spec/otcp/v1/`) and its lock are updated by the maintainers after the tag; this change does not touch them.

## Verification

- Every schema compiles with Ajv in JSON Schema 2020-12 strict mode; all 241 vectors validate against `schemas/vector.schema.json`, their params, results, job results and revert recipes against the method schemas, and their codes against the registries; `methods/index.json` matches the method table of PROTOCOL.md section 22.
- Every `op`, `mode`, `kind`, `layout`, `action` and `target` value is sent by a success vector, every method-specific error kind has an error vector, and every write method has a success vector with the whole write envelope. A set of planted defects (missing vectors, unregistered codes, wrong preconditions) each turns the checks red.
- `npm run gates`: see the pull request.
