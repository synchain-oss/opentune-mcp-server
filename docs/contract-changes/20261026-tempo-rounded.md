# Contract change: a switch of the view can round the tempo

- Date: 2026-10-26
- Frozen surface: `spec/otcp/v1/**`, `test/golden/**`
- Specification version: `1.0.0-rc.7` (wire version `1.0`), a correction inside the release candidate; the tag
  `spec-v1.0.0-rc.7` is set by the maintainers after approval and is not set yet.
- Implementation lines changed with it: `mock/ui.ts`, `src/render/text.ts`, `src/render/summary.ts`,
  `src/render/ui-effects.ts`, `src/tools/manage-ui.ts`, `mock/import.ts`.

## Background

The tempo field of the transport bar shows the tempo with one decimal. Each time the window switches view, the
keyboard focus leaves the field, and the field writes the value it shows back to the project and marks the project as
changed. A real window does this at every switch, as was checked on a started OpenTune: from the arrangement view to the
piano roll, from the piano roll back, and at the first switch after the start. A user who clicks a view button gets the
same.

So a project whose tempo has two decimals (120.27, which `transport.setTempo` can set) gets the tempo 120.3 when
`ui.setWorkspace`, or `ui.setSelection` with `openEditor` true that really switches the view, runs, and the project is
marked as changed. A tempo with one decimal or none (120, 120.3) is left as it is and `dirty` does not change. When the
window already shows the piano roll, `ui.setSelection` with `openEditor` true switches nothing and rounds nothing. The
specification said the opposite: "switching it never changes ...
and does not mark the project as changed" (PROTOCOL.md section 14.6, the descriptions of `ui.setWorkspace` and
`ui.setSelection`). That was true of everything the window shows, not of the tempo. This change says it as it is and
gives the effect a name, so that a client sees what happened to the tempo and can set it back.

It adds one side-effect name and one vector. Nothing is removed or renamed, and no method, capability, entity name,
error kind, warning code or reason code is added. The entity name `tempo` and the recipe of `transport.setTempo` are
the ones that exist already.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. A server that rounds the tempo and reports it
sends a side-effect name that older clients do not know, and an entity name that every client knows.

- The rule that makes this safe is in the specification already: clients ignore side-effect names they do not know
  (PROTOCOL.md section 2.3 rule 1) and accept entity names they do not know (rule 2); `tempo` is not unknown anyway.
  A client of the earlier text that does not know `tempoRounded` keeps working. It sees the tempo entry in `changes`,
  the new key in `sideEffects` and `dirty.after` true, like any other result.
- This server before this change, with an instance that reports the rounding: the summary lists "side effect
  tempoRounded, which this server does not know" in the generic words, the revert line still carries the
  `opentune_transport` call (a side effect's recipe is mapped as it is), and nothing is lost. Only the sentence with
  both tempi is missing.
- This server after this change, with an instance that does not report the rounding (the unofficial test build before
  it implements this, or a window-less run): nothing changes for it. On a real window of such a build, a tempo with
  two decimals is still rounded at every switch, and then it is not reported: `dirty` and the tempo differ from what
  the result says. The specification text of rc.7 before this change had the same blind spot.
- The mock and its vectors. The mock reports the rounding whenever a switch finds a tempo with more than one decimal;
  the fork's copy of the specification, which is pinned by hash, is synced by the maintainers. Every target runs the
  vector, a started OpenTune included, because the window rounds at every switch of the view.
- The names are fixed: `tempoRounded`, `fromBpm`, `toBpm`.
