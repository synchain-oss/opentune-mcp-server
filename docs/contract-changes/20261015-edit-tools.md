# Contract change: edit tools

## Background

This change adds the tools that edit a clip and its history: `opentune_set_clip`, `opentune_autotune_range`,
`opentune_edit_notes`, `opentune_undo` and `opentune_redo`. They extend the frozen `tools/list` catalog, so
`test/golden/tools-list.json` and the generated `docs/reference.md` change, and a new golden directory freezes what
the tools return. They are the first tools that hand the renderer's revert lines to an agent, which can call tools but
cannot send OTCP requests, so the shared renderer now turns a revert recipe into the tool call that carries it out;
that changes the rendering snapshots of every write result. The OTCP specification (`spec/otcp/v1/`) and the MCP
instructions are not changed.

| Tool                      | Input                                                                                                                                                                                                 | OTCP methods                                             | Capabilities         |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------- |
| `opentune_set_clip`       | `clip`, `expected_revision`, `key?`, `pitch_shift?`, `instance_id?`                                                                                                                                   | `content.setKey`, `content.setPitchShift`, `project.get` | `edit.v1`, `read.v1` |
| `opentune_autotune_range` | `clip`, `expected_revision`, `mode`, `ranges?`, `exclude?`, `scale?`, `retune_speed?`, `vibrato_depth?`, `vibrato_rate_hz?`, `note_split_cents?`, `dry_run?`, `replace_edited_notes?`, `instance_id?` | `content.autoTune`, `content.getDetails`, `project.get`  | `edit.v1`, `read.v1` |
| `opentune_edit_notes`     | `clip`, `expected_revision`, `ops[]`, `dry_run?`, `instance_id?`                                                                                                                                      | `content.editNotes`, `content.getNotes`, `project.get`   | `edit.v1`, `read.v1` |
| `opentune_undo`           | `undo_id`, `force?`, `instance_id?`                                                                                                                                                                   | `edit.undo`                                              | `history.v1`         |
| `opentune_redo`           | `undo_id`, `force?`, `instance_id?`                                                                                                                                                                   | `edit.redo`                                              | `history.v1`         |

All five return the write envelope through the shared renderer, with the shared loose output schema. None is read-only
by annotation. Only `opentune_autotune_range` is destructive by annotation: `notesOnly` replaces every note without an
undo entry and `regenerate` removes the notes in its ranges. `opentune_edit_notes` keeps every note and is not.
`opentune_edit_notes` is the largest entry (about 6.7 KB, limit 9 KB).

## Behaviour that is part of the contract

- `expected_revision` is the `clip_revision` from `opentune_get_project`, `opentune_get_notes` or the last write result
  for the clip. Only the aspects an
  operation depends on are forwarded: the key part for `content.setKey`, the content part for note edits and AUTO, and
  the key part as well only when the call uses the clip key (`scale: "clip"`). A change of another aspect does not
  conflict.
- `opentune_set_clip` with both `key` and `pitch_shift` makes two requests, key first, and reports each in `results`.
  When the key changed, the first sentence of the summary says that the key change cannot be undone. A request that
  fails, with an OTCP error or with a result that is not a write envelope, stops the call: nothing after it is sent,
  and when it is not the first, the error carries the results that took effect in `applied_before_error`.
- `opentune_autotune_range` never inherits the AUTO button's mode or the window's knobs; unset parameters are not sent.
  `exclude` is turned into the remaining ranges (at most 16). `mode: notesOnly` needs `replace_edited_notes: true`
  (a `dry_run` does not); without it nothing is sent and the error asks the user. The result's first sentence says
  that all notes were replaced and that it cannot be undone. `mode: reference` needs `reference.v1` and a placement id,
  and takes no ranges, scale, parameters or `dry_run`.
- `opentune_edit_notes` selects notes by index, by a source-audio time range, all, or by the condition
  `off_target_cents_over` (voiced notes whose sung pitch is more than N cents from their target). A condition is
  resolved to indexes by reading the notes; if they changed since the `clip_revision`, the call fails with
  `REVISION_CONFLICT(content_changed)` before anything is sent. Every condition is evaluated on the notes at
  `expected_revision`, before any op runs, and conditions on the same range share one read. A condition that matches no
  note sends nothing and returns a successful no-op. A repeated index in `indices` is sent once.
- The results of `opentune_set_clip`, `opentune_autotune_range` and `opentune_edit_notes` carry `clip_revision`, for the
  next write without reading the clip again. It holds the tokens the write result reports (`tokens`, section 14.5 of
  the protocol) and, for an aspect the result does not report, the token the caller passed (a note edit does not touch
  the placement, so its geometry token stays as passed; a stale one makes a later write conflict, never overwrite). It
  is null, with `nullReasons.clip_revision`, when the result reports no tokens for the clip's content.
- A revert recipe in a write result is rendered as a tool call: `content.setKey` and `content.setPitchShift` as
  `opentune_set_clip` with `key` or `pitch_shift`, to which the agent adds the latest `clip_revision` as
  `expected_revision`; `edit.undo` and `edit.redo` as `opentune_undo` and `opentune_redo` with `undo_id`. The line keeps
  the recipe as OpenTune sent it in `revert` and the call in `restore`; a recipe that needs consent says that it may be
  carried out only after the user explicitly agrees. For a recipe no tool performs yet, `restore` is null and the line
  says that the user can restore the state by hand in the OpenTune window. The undo line names `opentune_undo` and
  `undo_id` instead of the OTCP parameter.
- `opentune_undo` / `opentune_redo` always send `expectedUndoId`; `force` is sent only when `force` is true and the
  description restricts it to an explicit request of the user.

## Compatibility

There is no earlier version of these tools. Tool names freeze with the first npm release. The renderer's revert lines
gain the member `restore` and change their wording; no released client has seen the old wording.
