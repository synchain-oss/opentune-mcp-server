# Contract change: app.quit and the tool opentune_quit

- Date: 2026-10-26
- Frozen surface: `spec/otcp/v1/**`, `test/golden/**`, the description and input schema of the new tool `opentune_quit`
- Specification version: `1.0.0-rc.6` → `1.0.0-rc.7` (wire version `1.0`, unchanged; `1.0.0-rc.7` is still unreleased, this
  change joins its section). The tag `spec-v1.0.0-rc.7` is set by the maintainers after approval.
- Implementation lines changed with it: `mock/app.ts`, `mock/jobs.ts`, `mock/server.ts`, `src/tools/quit.ts`,
  `src/tools/index.ts`, `src/otcp/instances.ts`, `src/errors/next-step.ts`, `test/contract/*` (the runner), and the
  stand-in executable and the scenario of the token canary under `test/support/`.

## Background

An agent that has finished the work with a user can save the project, but it could not close OpenTune: no method did what
the close button of the OpenTune window does, so the user had to do it. Closing the program after the work is done is an
operation the window offers, so this change adds it.

The window is not a model to copy without a change. OpenTune Standalone uses the stock `StandaloneFilterWindow` of JUCE.
Its handler of the close button (`StandaloneFilterWindow::closeButtonPressed` in `juce_StandaloneFilterWindow.h`) does two
things: `pluginHolder->savePluginState()`, then `JUCEApplicationBase::quit()`. It asks nothing, **also when the project has
unsaved changes**, and the editor's destructor saves only the window size and restores the ASIO sample rate, not the
project. A client that quit through the same path would lose the user's unsaved work without a word. The method therefore
refuses while the project has unsaved changes, in the way `project.open` does (`discardUnsaved`, section 20.2 rule 3), so
that the consent to lose them is a separate, explicit step of the end user. The behaviour of the window itself is
upstream's and is not changed here.

The change adds one method, one capability, one reason of `BUSY`, one null reason, one member of the vector format and
nine vectors. Nothing is removed or renamed, and no error kind or warning code is added.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. The method is new and the capability tells a client
whether an instance has it (PROTOCOL.md section 2.3 rule 5), so nothing depends on the version number.

- A client of rc.6 with a server of rc.7 never sends `app.quit` and sees what it saw before, plus one more capability in
  `session.hello`, which it ignores. The new reasons appear only in the results of the new method.
- A client of rc.7 with a server of rc.6 does not find `app.quit` in `session.hello`. A client that sends it anyway gets
  `UNSUPPORTED(unknown_method)` (-32601) from such a server, and nothing is closed. `opentune_quit` checks the capability
  first and sends nothing: it answers with `UNSUPPORTED(capability_missing)` and a next step for the user, who closes the
  OpenTune window after the project is saved (the window quits without asking about unsaved changes). The test build of
  `0.2.0` follows rc.6, so it answers this way until it is updated.
- The unofficial OpenTune test build must implement `app.quit` and report `app.quit`; its copy of the specification and its
  runner are updated separately. It must answer first and quit afterwards, refuse with unsaved changes unless
  `discardUnsaved` is true, and exit on its own within `exitDeadlineMs`, with exit status 0 and its discovery file removed.
  Its runner can end a run of vectors on a vector with `endsSession`; the format says how (restart the target).
- A client that reads the new vector member `endsSession` and does not know it ignores it and fails the three vectors that
  end the instance only by the connection that closes; the format asks the runner to restart the target after them.
- The mock changes only what this record names. A client that uses the mock in its own tests and sends `app.quit` now
  makes the mock stop, as OpenTune would.
- The tool count rises from 27 to 28. `opentune_launch` still never closes OpenTune; only the new tool asks it to close,
  and only OpenTune ends its own process: this server never ends a process.
