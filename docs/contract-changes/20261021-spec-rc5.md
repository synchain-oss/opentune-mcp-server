# Contract change: OTCP specification 1.0.0-rc.5

- Date: 2026-10-21
- Frozen surface: `spec/otcp/v1/**`
- Specification version: `1.0.0-rc.4` → `1.0.0-rc.5` (wire version `1.0`, unchanged), proposed as the text of 1.0.0.
  The tag `spec-v1.0.0-rc.5` is set by the maintainers after approval.
- Implementation lines changed with it: `mock/prefs.ts`, `mock/server.ts`, `mock/tracks.ts`, `mock/ui.ts`,
  `src/errors/next-step.ts` (the next step of `no_editor_window`), `src/errors/reason-retryable.ts` (its retryability).

## Background

Implementing rc.4 in OpenTune showed five places where the text said less than OpenTune does or more than was meant:
the `prefsApply` job checks the busy state a second time, a hidden track cannot be duplicated, the methods that act
through the editor window refuse to run without one, closing the first-run overlay in a real window usually changes
the view only, and two sentences (section 12.6 rule 1, the `trackIdMap` of section 9) were too broad or too short.
This release candidate records them. It adds no method, member, capability, error kind or warning code; it
adds one reason (`UNSUPPORTED(no_editor_window)`), two vectors, and widens the description of one existing reason.

## Interoperability

Both versions are release candidates of the same wire version `1.0`; clients decide by capabilities, not by version
(PROTOCOL.md section 2.3 rule 5).

- A client of rc.4 with a server of rc.5 sees only kinds that rc.4 registered, and one reason that it did not:
  `UNSUPPORTED(no_editor_window)` from a method that needs the editor window, which happens only in a window-less
  test build. The other cases it sees are `INVALID_ARGUMENT(track_hidden)` from `track.duplicate` and
  `BUSY(modal_open)` as the error of a `prefsApply` job (retryable), whose reasons rc.4 registered. An rc.4 client
  does not know `no_editor_window`; by PROTOCOL.md section 2.3 rule 2 it accepts the unknown reason and branches
  only on the kind `UNSUPPORTED`, so it gets the kind-level next step and is not directed to upgrade the build.
  This server's `nextStep` for it is already aligned, and the fork will switch to the new code afterwards. A
  `ui.dismiss` that closes the overlay may have empty `changes` and the undo reason `not_persisted_state`, which the
  write envelope always allowed.
- A client of rc.5 with a server of rc.4 may see a hidden track duplicated into the first hidden slot, preferences
  applied although a dialog opened after the call, or `onboardingShown` reported as changed when the preference was
  already set. Such a client still reads every result as it comes: the result reports what happened.
- OpenTune's implementation already behaves this way: its own tests check the refusal of a hidden source track, the
  second busy check of the `prefsApply` job, the refusals without an editor window and the closing of the overlay.
  Its copy of the specification is updated separately.
