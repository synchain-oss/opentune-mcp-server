# Contract change: OTCP 1.0.0-rc.9

- Date: 2026-10-31
- Frozen surfaces: `spec/otcp/v1/**`; the result snapshots of the save tools (`test/golden/project-files/*.json`: the
  sentence about the media folder and the path in `mediaFolder`); two new files under `test/golden/render/`. The
  `tools/list` snapshot, the instructions snapshot and every tool description are unchanged.
- Specification version: `1.0.0-rc.8` → `1.0.0-rc.9` (wire version `1.0`, unchanged). The changelog section of
  `1.0.0-rc.9` is marked unreleased; the maintainers set its date and the tag `spec-v1.0.0-rc.9` after approval.
- Implementation lines changed with it: the mock, the rendering text of the warnings and the save tools follow in the
  same pull request, as for `20261028-project-save-copy.md`.
- Tool names, the set of tools, their arguments and the set of OTCP methods do not change.

## Background

The OpenTune fork is rebased onto the upstream release 1.8.2 (the last rebase before 1.0.0), and this is the last time
the text of the specification changes before 1.0.0, so the text has to say what that release does. Four places differ:

1. The preference `renderingPriority` can leave a client believing that the GPU runs. With `gpuFirst`, OpenTune tries the
   GPU each time the vocoder loads and runs on the CPU when that fails, and nothing in the result of `prefs.set` or in
   `session.info` said so at the time of the call. The fields that describe the backend had no description either.
2. When `audio.set` switches the device type or the output device, OpenTune restores the sample rate of an ASIO device
   before it switches, as its audio settings page does. The text said that a failure of that restoration is a failure to
   open the device, with a rollback. OpenTune does not roll back: the switch goes on, and the driver can run at another
   sample rate than before.
3. The media of a project. The text said that a save, a Save As and a copy write the media into one folder
   `Project_Media` that every project file of the directory shares, and that an older media file of the same name is
   replaced, so another project's media could be replaced. OpenTune now writes them into a folder named after the target
   project file, and always writes them again.
4. Two behaviours that the text did not state: the undo description follows the language of the OpenTune window, and an
   export drains render blocks that are set aside for a delayed retry before it starts.

The change adds two warning codes and changes only text and descriptions otherwise. No method, param or result member is
added, removed or renamed. No reason code is added or retired.

### The two warnings

- `BACKEND_FALLBACK`: carried by the result of the `prefsApply` job of `prefs.set` when the call changed
  `renderingPriority` to `gpuFirst` and the backend that OpenTune reports when the job ends is `cpu`. `subject` is null,
  `data` is `{"requested": "gpuFirst", "actual": "cpu"}`. The backend is read once, when the job ends. A job does not wait
  for a vocoder that was not ready before the call, so such a job can read the backend from before the change; the
  warning is then absent or stale, which section 12.7 rule 7 says.
- `ASIO_RATE_NOT_RESTORED`: carried by the result of `audio.set` when the call changed `deviceType` or `outputDevice`
  and OpenTune could not restore the sample rate of an ASIO device before the switch. `subject` is `{"singleton":
"audioDevice"}`, `data` is `{"deviceName": <string>, "sampleRateHz": <number>}`: the ASIO device and the rate in Hz
  that OpenTune tried to restore. The call succeeds and nothing is rolled back.

### The rendering text

The rendering templates of the server are English only by the policy of this repository (`src/render` holds English
text, and the Chinese wording is in the Chinese documents), so the Chinese wording of the two warnings is in
`docs/TROUBLESHOOTING.zh-CN.md` and not in `src/render`.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. A warning code that a client does not know is
accepted and shown by its `message` (PROTOCOL.md section 2.3), so nothing depends on the version number.

- A client of rc.8 with a server of rc.9 receives two warnings it does not know and ignores them, and the results are
  otherwise as before.
- A client of rc.9 with a server of rc.8 never receives the two warnings. It does not conclude from their absence that
  the GPU runs or that the ASIO rate is the same, and a server of rc.8 is shown only by its version.
- An OpenTune that follows rc.8 but is read by this repository keeps the media folder `Project_Media`. This server
  writes nothing into a media folder of OpenTune; it copies the folder next to a project file that it is about to replace
  into `<name>.oldversion`, and it takes `<name>_Media` when that folder exists and `Project_Media` otherwise, so both
  generations of project files get their audio in the old version.
- The unofficial OpenTune test build must follow this text. The list of what the OpenTune fork has to change, with the
  exact shapes, is below. The test build `synchain-test/v1.8.0-ctl.3` has the same OpenTune and the same control
  interface as `ctl.2` and only adds a macOS package; it implements rc.8 and is listed as such in
  `docs/COMPATIBILITY.md`. A build that implements rc.9 is not listed yet.

### What the OpenTune fork has to change

1. `prefs.set`: when the `prefsApply` job ends and the call changed `renderingPriority` to `gpuFirst` and
   `session.info` `processing.backend` is `cpu`, add the warning `BACKEND_FALLBACK` with `subject` null and `data`
   `{"requested": "gpuFirst", "actual": "cpu"}`.
2. `audio.set`: when the restoration of the ASIO sample rate fails, continue the switch and add
   `ASIO_RATE_NOT_RESTORED` with `subject` `{"singleton": "audioDevice"}` and `data` `{"deviceName", "sampleRateHz"}`.
   Do not fail with `IO_ERROR(device_open_failed)` and do not roll back for this case; keep that reason for a device
   that cannot be opened.
3. `export.start`: when the render blocks set aside for a delayed retry cannot be drained before the export starts, fail
   the job with `NOT_READY(export_wait_timeout)` (retryable). No new reason.
4. Projects: write the media of a save, a Save As and a copy into `<target file name without .otproj>_Media` beside the
   target project file, always through a temporary file, and report `ALREADY_EXISTS` of `project.saveCopy` by looking
   at the `.otproj` alone.
5. Undo entries: the `description` is the text of the undo menu in the language of the OpenTune window.
6. Runner: understand `given.gpu` and `given.audio.asioRateRestoreFails`, or report the four new vectors as skipped with
   the reason that the target cannot establish them (they cannot on a machine whose GPU and audio drivers the runner
   does not control).

## Open points for the maintainers

- Each autosave copy now gets a media folder of its own (`<copy name>_Media`) in `<name>.autosave`, because OpenTune
  names the folder after the project file. This server never deletes a folder, so rolling the older copies away leaves
  their media folders and the space taken grows by the audio of the project with every copy (at most the audio times the
  number of copies written). The change that removes the sibling folder together with the copy needs a decision of the
  maintainers; the documents say that the folders are left.
- The shape of the data of `ASIO_RATE_NOT_RESTORED` is defined here from the card and was not compared with the fork.
- No reason is retired. The text had no reason for a failed ASIO restoration (it was described as `device_open_failed`),
  so there is nothing to mark with `retiredIn`.
