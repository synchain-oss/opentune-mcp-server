# Contract change: timing workflow for a whole song

## Background

Fixing the timing of a whole sung take with the `beat-grid` skill did not work in practice. A take of about 150 seconds
had 1152 notes after automatic tuning:

- `opentune_get_notes` returns a few dozen notes per page, so reading all of them took more than ten calls, and the
  skill needs all of them in one JSON file for `timing-plan`.
- Automatic note splitting cuts a glide into touching pieces of 10 to 20 ms. `timing-plan` treated each piece as a
  rhythm onset: 614 were flagged, almost all of them pieces. Merging touching pieces by hand reduced them to 56.
- `opentune_edit_timing` and `timing-plan` handled at most 8 operations per call, so 614 suggestions needed dozens of
  rounds, each re-reading every note.
- A plugin loaded with `--plugin-dir` has no `CLAUDE_PLUGIN_DATA` in the shell, so `beat-grid` could not find its data
  folder; the subcommands had no help.
- The skill asked the user whether the backing track and the vocal start together, a question a program can answer.

This change makes `opentune_get_notes` write all notes into a file, raises the operation limit of
`opentune_edit_timing`, and changes the skill and its script. No other tool changes. The OTCP
specification (`spec/otcp/v1/`) and the MCP instructions are not changed: `content.editTimeGrid` already takes up to 64
`moveHandles` entries, and `content.getNotes` already pages with a cursor.

The maintainer approved changing the interface of the two tools for this.

## `opentune_get_notes` with `output_path`

`output_path` is optional. Without it nothing changes: the same pages, the same result. With it the tool reads every
page of the range itself (`content.getNotes`, 500 notes per page) and writes all notes of the range to one UTF-8 JSON
file. The file has the members of a normal result (`clip`, `clock`, `clip_revision`, the tuning frequency, `notes[]`
with the same member names and units, `next_cursor` null); the tool result is a small summary: `output.path`,
`output.renamed`, `output.noteCount`, `output.bytes`, `clip_revision` and the clock.

- **Path.** Same rules as the export path (`src/paths/`): quotes, `file://`, `~` and `/mnt/<drive>/` are normalized;
  relative, UNC, `\\?\`, `\\.\`, drive-relative paths and alternate data streams are refused; only `.json` is accepted.
  The folder must exist; it is never created.
- **No overwrite.** A taken name gets the next free `<name> (2).json`, up to `(999)`, as exports do; all taken is
  `ALREADY_EXISTS` (`target_exists`). The data goes to a temporary file in the same folder and is then linked to the
  free name (a copy that fails when the name exists, where hard links are not available), so no moment exists at which a
  file could be replaced or a half-written file stays behind.
- **Consistency.** If the clip changes while the pages are read (another revision or a rejected cursor),
  the result is `REVISION_CONFLICT` (`content_changed`), nothing is written and the call can be repeated unchanged.
- **Limits.** `cursor` and `limit` together with `output_path` are `INVALID_ARGUMENT`; a range of more than 50,000 notes
  is `INVALID_ARGUMENT` (`range_too_large`) with advice to read a narrower range; a failed write is `IO_ERROR`
  (`write_failed`).
- **Annotations.** The tool writes a file, so `readOnlyHint` and `idempotentHint` are now false (`destructiveHint` stays
  false: nothing is deleted or replaced). A client that approves read-only tools automatically asks about
  `opentune_get_notes` from now on. OpenTune itself is not changed by the tool.

## `opentune_edit_timing` with up to 64 operations

`ops` takes 1 to 64 entries (was 8), matching the limit of `moveHandles` in the specification. Each `shift` and `move`
still is its own OTCP request and its own undo step, applied in order with the grid revision of the previous one;
`seed` still must be the only operation.

- A call of up to 8 operations returns what it returned before.
- A call of 9 to 64 operations returns compact steps: per step the operation number, `op`, how many handles moved and
  were limited, the `undo_id`, and the moves as `[handle_id, before_output_sec, after_output_sec, requested]` rows (the
  last item only when a move was limited), at most 6,000 characters of rows in all (`moves_omitted` counts the rest;
  `moves_total` and `moves_listed` for the call). The result stays within the output budget; the handle list in the
  result is cut to 40 entries (the count of all of them is given).
- A call that has run 40 seconds sends no further operation and says so (`stopped`: `reason`, `applied`, `total`,
  `next_operation`, and the first sentence). What was applied stays applied, and the result has the `clip_revision` to
  go on with.
- If an operation is refused, the error still says how many were applied and gives `completed` (compact above 8 steps).

## The beat-grid skill and its script

- `timing-plan` accepts the file `opentune_get_notes` writes (the multi-page format of the old skill still works).
- It merges fragments before comparing: a note joins the chain before it when it starts less than `--merge-gap-ms`
  (default 30) after the chain ends and its pitch is within `--merge-cents` (default 300) of the previous note's; the
  start of a chain is the rhythm onset and the operation covers the whole chain. A lone note shorter than
  `--min-note-ms` (default 60) gets no suggestion. The values, with the reason for each, are in `settings` of the
  output and in `SKILL.md`; `merge` in the output counts the notes, chains and onsets.
- `maxOpsPerCall` is 64 and `calls[]` has every batch. Only `calls[0]` carries an `expected_revision`; the others are
  previews with `null`. After a batch the skill plans again, because `content.shiftTiming` moves the handles in its
  range and leaves the others (the audio between a moved handle and one that stays is stretched), a move next to a
  neighbour may be limited, and every call changes the grid revision, so the later suggestions of the same plan no
  longer match the notes.
- `--home` is accepted by every command and is passed on every command in `SKILL.md`; priority `--home`, then
  `OPENTUNE_BEATS_HOME`, then `CLAUDE_PLUGIN_DATA`; `status` reports which one it used. `<command> --help` prints the
  usage of one command and exits 0.
- New command `align --vocal <wav> --backing <wav>`: both files get an onset-strength envelope at 100 Hz, which are
  cross-correlated within 2 seconds; the output is the lag in seconds and a confidence (the best peak over the next one,
  confident from 1.5). It reads 16, 24 and 32 bit PCM and 32 bit float WAV with Node's own modules. The skill asks the
  user only when the check is not confident.

## Installed analyzer: `status` first

An analyzer that was already installed was treated as missing while the manifest said the release was not published:
the install plan listed Problems and said not to retry, and `SKILL.md` said to stop, so the beat-grid workflow was given
up. `SKILL.md` now starts with `status` and skips the install section when `installed` is true and the model is there.
`install` (the plan and `--yes`) reports `already installed` (version, folder, models; `--yes` adds
`alreadyInstalled: true`), exits 0 and downloads nothing when the program and the models asked for are there, without
listing Problems; the release state only blocks an install when nothing is installed. `status` leaves out the
unpublished-release note for an installed analyzer.

## Security: `allowed-tools` removed from the skill

`SKILL.md` had an `allowed-tools` line. While the skill is loaded, Claude Code lets the tools it lists run without asking,
so it allowed any shell command and file read or write without the user being asked for as long as the skill was active.
A skill has no need for that: the script it runs is a plain `node` command. The line is removed, so the user's own
permission settings apply to every command of the skill.

## Compatibility

| Client or server                          | Effect                                                                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| New client, new server                    | As described above.                                                                                                                        |
| Old client, new server                    | Keeps working: `output_path` is optional, a call of 8 operations or fewer returns the same result. It does not know the new members.       |
| New client, old server                    | `output_path` is refused as an unknown argument and more than 8 operations are refused, so the skill's steps for a whole song do not work. |
| Client that auto-approves read-only tools | `opentune_get_notes` is no longer read-only (it can write a file), so such a client asks about it.                                         |
| OpenTune (fork)                           | No change: both tools use methods that exist (`content.getNotes`, `content.shiftTiming`, `content.editTimeGrid`).                          |
