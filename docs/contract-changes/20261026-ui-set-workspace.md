# Contract change: ui.setWorkspace and the op switch_view

- Date: 2026-10-26
- Frozen surface: `spec/otcp/v1/**`, `test/golden/**`, the description and input schema of `opentune_manage_ui`
- Specification version: `1.0.0-rc.6` → `1.0.0-rc.7` (wire version `1.0`, unchanged). The tag `spec-v1.0.0-rc.7` is set by
  the maintainers after approval.
- Implementation lines changed with it: `mock/ui.ts`, `mock/server.ts`, `src/tools/manage-ui.ts`,
  `src/render/revert.ts`, `src/render/ui-effects.ts`.

## Background

`opentune_manage_ui` could open the piano roll (`focus_clip` with `open_editor`) but no operation led back. The OTCP
method `ui.setSelection` only switches the window to the piano roll, and its revert recipe deliberately does not switch
the window back, so an agent that opened the piano roll could not close it again. An instance has two views, the
arrangement view and the piano roll, and the transport bar has one button for each. This change adds a method with the
same effect as those buttons, a capability that tells a client whether an instance has it, and the op `switch_view` of
`opentune_manage_ui` that sends it. Closing the piano roll is switching to the arrangement view.

It adds one method, one capability, one entity name and five vectors. Nothing is removed or renamed, and no error kind,
warning code or reason code is added.

## Interoperability

Both versions are release candidates of the same wire version `1.0`. The method is new and the capability tells a
client whether an instance has it (PROTOCOL.md section 2.3 rule 5), so nothing depends on the version number.

- A client of rc.6 with a server of rc.7 never sends `ui.setWorkspace` and sees what it saw before, plus one more
  capability in `session.hello`, which it ignores. The entity name `ui` appears only in the result of the new method,
  so no result of an existing method changes.
- A client of rc.7 with a server of rc.6 does not find `ui.workspace` in `session.hello`. A client that sends
  `ui.setWorkspace` anyway gets `UNSUPPORTED(unknown_method)` (-32601) from such a server, and nothing is changed. `opentune_manage_ui` with op `switch_view` checks the capability first and sends nothing: it answers with
  `UNSUPPORTED(capability_missing)` and a next step that asks the user to click the arrangement view or piano roll
  button in the transport bar. The other ops of the tool keep working, because they ask for `ui.bridge`.
- The unofficial OpenTune test build must implement `ui.setWorkspace` and report `ui.workspace`; its copy of the
  specification and its runner are updated separately. Until then `switch_view` answers as described above. The
  implementation is expected to change the view only: if it generates notes or queues work on a switch, the
  specification text ("never generates or queues anything") and the vectors have to be changed again, and the
  maintainers decide how.
- The mock changes only what this record names. A result of `ui.setWorkspace` names its change by the `ref`
  `{"singleton": "workspace"}` of the entity `ui`; a client that does not know the entity name treats it as an unknown
  entity and keeps its fields.
