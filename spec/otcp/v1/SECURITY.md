# OTCP v1 threat model

This document describes what the OpenTune Control Protocol protects, against whom, and with which rules of [PROTOCOL.md](PROTOCOL.md). It also lists the risks that remain. To report a vulnerability, follow the security policy at the root of the repository that contains this specification; do not open a public issue.

## 1. Assets

| Asset                        | Why it matters                                                      |
| ---------------------------- | ------------------------------------------------------------------- |
| The user's project and audio | Edits, deletions and overwritten files can destroy work.            |
| Files on disk                | Export and save write files; import and open read them.             |
| The user's global settings   | Preferences and the audio device outlive the session.               |
| The control token            | Whoever has it can control the instance.                            |
| The server proof             | Lets a client recognise the genuine instance.                       |
| The AI client's decisions    | Text returned by OpenTune reaches an AI model, which may act on it. |

## 2. Trust boundaries

| Party                                                                   | Trusted? | Reason                                                                                                                                                              |
| ----------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Processes of the same operating-system user                             | yes      | They can already read the user's files, the discovery file and OpenTune's memory, and control the user's desktop. The protocol does not try to defend against them. |
| Other operating-system users on the same computer                       | no       | They must not read the token, connect successfully or plant a discovery file.                                                                                       |
| Web pages in a browser on the same computer                             | no       | A page can make the browser open TCP connections to `127.0.0.1` and send HTTP requests to any port.                                                                 |
| Other computers                                                         | no       | They must not reach the port at all.                                                                                                                                |
| Text inside projects, audio files and logs (names, metadata, log lines) | no       | It can be written by anyone who produced the file and may be aimed at the AI client (prompt injection).                                                             |
| The AI model driving the client                                         | partly   | It acts for the user, but its inputs can be manipulated; destructive actions need the user's own consent.                                                           |

## 3. Threats and mitigations

| #   | Threat                                                                                                                                             | Mitigations (PROTOCOL.md section)                                                                                                                                                                                                                                                                                                        |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1  | Another computer connects to the port.                                                                                                             | The server listens only on the literal `127.0.0.1`, never on other addresses (3.1). Clients connect only to `127.0.0.1` and never resolve host names (3.1).                                                                                                                                                                              |
| T2  | A web page drives the port through the browser (cross-protocol request).                                                                           | The first line must be a single JSON object that is a valid `session.hello` request, within 2 s and 8 KiB, or the connection is closed without a single byte (3.5); an HTTP request is never a valid first line, and the page receives nothing it could read. A browser cannot read the discovery file, so it cannot know the token (5). |
| T3  | Another OS user or a web page guesses the token.                                                                                                   | At least 128 random bits from the operating system's secure generator (4.5); constant-time comparison (4.2); identical fixed failure responses that reveal nothing (4.2, Appendix A); at most 8 unauthenticated connections (3.4).                                                                                                       |
| T4  | Another OS user reads the token from the discovery file.                                                                                           | The discovery directory is private to the user: on Windows it is in the user's local application data folder; on POSIX systems the directory is mode 0700 and owned by the user, the file mode 0600, and the server refuses to start if the directory fails these checks (5.1, 5.2, 6.4).                                                |
| T5  | Another OS user plants or replaces a discovery file to send the client to a port it controls.                                                      | Same directory protection (5.2). Files are created exclusively without following symbolic links and moved into place by rename (5.2). After `session.hello` the client checks that the server proof, instance id and process id match the file, and stops otherwise (4.3).                                                               |
| T6  | A stale discovery file names a port that another process now uses.                                                                                 | The client checks process liveness together with the process start time (5.4) and verifies the server proof after connecting (4.3). The token it sent belongs to a dead instance and is worthless.                                                                                                                                       |
| T7  | The token or server proof leaks through results, logs or diagnostics, and from there into an AI conversation or a bug report.                      | They appear only in the discovery file and in `session.hello` (4.5); `app.getLog` redacts them (20.2); error details never contain them (17.1). New values are generated on every start (4.5).                                                                                                                                           |
| T8  | Denial of service by a local process: many connections, huge lines, slow senders, deep nesting.                                                    | Limits on unauthenticated connections, sessions, line length, in-flight requests, idle time and nesting depth (3.2, 3.4, 3.5). Main-thread work has a dispatch deadline (13.1).                                                                                                                                                          |
| T9  | Text in a project or file instructs the AI to do something destructive.                                                                            | Names, paths, metadata and log lines are returned only as JSON string values, never mixed into labels or details (20.2). Destructive methods require explicit confirmation params, and the consent must come from the user, never from a result (20.2).                                                                                  |
| T10 | A path in a request makes OpenTune read or write somewhere unexpected (relative, network, device or alternate-stream paths, or overwriting media). | Strict validation of the raw path string before any file-system access, with no normalization by the server (20.1). Exports never write to loaded sources or project media and do not overwrite unless asked (19).                                                                                                                       |
| T11 | A request that timed out runs later, after the client assumed it failed.                                                                           | Abandoned requests never execute (13.1); `TIMEOUT` always has `executed` false (17.4).                                                                                                                                                                                                                                                   |
| T12 | The AI overwrites the user's own work: undoing the user's edit, or writing over a concurrent edit.                                                 | Writes are refused while the user is busy (13.2); expected tokens detect concurrent changes (10); `edit.undo` and `edit.redo` require the expected undo entry and refuse others unless the user asked (15.3).                                                                                                                            |
| T13 | A result hides a side effect, so the AI or the user does not know what changed.                                                                    | Every write returns the world revision difference, side effects, warnings and how to undo or revert (14, 15, 18).                                                                                                                                                                                                                        |
| T14 | Global settings changed by the AI stay changed after the session.                                                                                  | Preference and device changes report the previous values as revert recipes (15.2).                                                                                                                                                                                                                                                       |
| T15 | The control API runs in a build or at a time the user did not intend.                                                                              | It is a build option that is off by default, and even then starts only when explicitly enabled at launch (6).                                                                                                                                                                                                                            |

## 4. Residual risks

1. **Same-user processes are trusted.** Malware running as the user can read the token and control OpenTune. This is outside the protocol's protection, as it is for every other application of that user.
2. **Overridden directories.** With `--control-api-dir=` or `OPENTUNE_DATA_DIR`, the discovery directory is whatever the launcher chose. On POSIX systems the server still checks it (5.2); on Windows the protection depends on the access rights of that directory. Use these options only with private directories, as tests do.
3. **The token goes to whoever listens on the port.** The client sends the token before it can verify the server proof. If OpenTune has exited and another process took the port, that process receives a token that is already invalid; the client then detects the mismatch and stops.
4. **Interleaving with the user.** Some user actions are not covered by busy checks; tokens detect the effects on dependent writes, but not every interleaving can be prevented (13.4).
5. **OpenTune's own behaviour.** Known OpenTune behaviours, such as undo entries that do not restore split, merged or deleted clips, are reported rather than fixed (15.4).
6. **The AI can still be misled.** The protocol keeps untrusted text out of structural fields and requires user consent for destructive actions, but it cannot stop a model from being persuaded by text it reads. Clients must present results to the model as data.
